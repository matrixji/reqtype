# ReqType 官网同步

目标是让官网准确反映实际可用产品。先判断差异，再选择网站代码部署、发行数据同步，或无需操作。不要仅因桌面项目出现新提交就部署。

## 输入与证据

- 以 ReqType 仓库根目录为基准定位 `../reqtype-site`，不依赖调用时的工作目录。读取两仓库适用的 `AGENTS.md`、Git 状态与相关 Skills；保留用户未提交内容，缺少网站仓库时报告缺失，不自行创建替代站点。
- 先读 [官网发布契约](../../../docs/website-release.md) 和网站的 `README.md`、`.agents/skills/reqtype-site-release/SKILL.md`。发行同步再读 [交付 Skill](../reqtype-delivery/SKILL.md)；实际脚本与服务实现优先于过时说明。
- 从当前源码、`README.md`、相关 `docs/`、`release-notes/`、测试记录提取用户可见变化。检查本地差异、远端 main 与正式 GitHub Releases，记录比较的提交与版本；使用 `gh` 或可用 GitHub 工具获取当前 Release 的最终标题、正文和资产。不要把本地版本号当作已发行证据。
- 对照网站 `public/index.html`、`public/app.js`、样式、截图资源及线上 `/api/site`、`/api/releases`。查清文案来自静态页面还是 API 状态：当前 `app.js` 会用 API 覆盖 headline、description、tagline，改 HTML 或初始化默认值不代表已有线上状态会更新。
- 将已发行、已合入但未发行、未提交／开发中分开。默认官网下载介绍对应已发行能力；规划或开发中能力只有确有必要时明确标注。不能把交叉打包、设计文档或测试目标当作实际运行通过。

## 判断与执行

给出简短的差异依据（产品证据 → 官网现状 → 拟改位置），然后在已授权范围内执行：

| 发现 | 行动 |
| --- | --- |
| 纯内部重构、测试变化，或官网已准确覆盖 | 不改站点、不部署，说明依据 |
| 功能说明、限制、截图、导航或页面交互已过时 | 最小修改网站源码及对应回归，验证后部署网站 |
| GitHub 已正式发行，但官网发行数据缺失 | 使用桌面仓库现有 deploy 流程同步该 Release；通常无需修改网站源码 |
| 发行数据已一致，但线上页面仍是旧代码 | 核对可发布源码及线上差异后，仅部署网站 |
| 仅开发分支新增能力，尚未发行 | 不宣传为当前下载版能力；必要时准备明确标注的文案 |
| 无法确认线上状态或发行证据 | 可继续本地准备；明确未知项，不据此盲目上传或宣称无需更新 |

用户要求“判断、按需修改并发布”已授权这次必要的网站部署，不重复索要确认。仅要求评估、草拟或创建 Skill 时不发布；授权不足时先完成可审阅的变更和验证，再说明待授权的具体动作。官网同步不自动授权桌面应用发版、推送 tag 或轮换凭据。

## 修改与本地验证

- 按网站现有结构修改，使用真实、对应版本的应用截图；不生成虚构产品界面。截图和桌面验证优先后台运行，不抢占用户焦点。
- 遵守各仓库分支与 PR 约定；ReqType 修改走工作分支和 PR，通过全部 `CI required` 后 squash 合并，不直接推送 main。分别检查两仓库 diff，不将用户无关文件提交或带入部署。
- 网站运行 `npm run check` 与 `npm test`。行为变化补有意义的回归；纯文字调整不机械新增测试。页面变化在本地浏览器检查真实渲染、窄屏、截图切换、各架构下载及无发行包／请求失败状态。
- 本地服务使用临时独立 `DATA_DIR` 和端口，不复用生产数据或发布凭据。涉及桌面客户端上传契约的修改，同步对应 HTTP 回归与文档。

## 发布与验收

**网站代码：** 先检查网站当前 `scripts/deploy.sh` 与待同步文件。现有脚本会同步工作目录，并非只同步已提交文件；若含无关改动，使用仅含已验证目标文件的隔离工作树或导出目录，不能悄悄夹带用户工作。按网站说明在其根目录运行 `bash scripts/deploy.sh <ssh-host>`，当前默认目标为 `c2`。代码部署到 `/opt/reqtype-site/app`，保留父目录 `.env` 与 `data`、单实例运行、已有证书及其他 Nginx 服务。记录可恢复的旧代码版本；失败时先定位实际状态，仅恢复本次代码／配置，不能以代码回退覆盖发行数据。

**发行数据：** 使用 ReqType 当前 `scripts/deploy-release.mts` 与 Actions deploy job 的接口，读取已发布 GitHub Release 的最终 Notes、三个 ZIP、manifest 与校验和，不手写替代发行事实。先查官网状态：同版内容及哈希相同则只验证；同版冲突或已有更高版本则停止上传，不覆盖、降级或伪造新版本。GitHub 已发布时只重跑失败的 deploy job，不重跑 publish、移动 tag 或替换资产。beta 不更新稳定首页。

**动态文案：** 当前首页介绍由正式 Release Notes 摘要同步。若仅需更正已存储的动态文案，先核实服务是否已有独立配置接口；没有则报告这一限制并在授权范围内实现、测试合适的配置更新机制，不假造发行版、不直接改线上 `state.json`，也不声称部署静态 HTML 已生效。

Token 仅由现有 Secret／环境安全传入，不输出 `.env`、完整容器环境或带凭据命令；凭据缺失时交付已验证结果并指出具体阻塞。网络响应不明确先只读查询状态；无法确认时停止自动重试。

发布后检查容器健康、HTTPS `/healthz`、实际页面、`/api/site` 与 `/api/releases`，核对本次文案和版本。验证已发布平台下载跳转及 HEAD／Range；发行同步还要核对实际文件 SHA-256。检查保留策略范围内的历史版本仍可访问，不要求已按最近 10 版策略清理的版本继续存在。

最终报告：是否需要同步及依据、实际修改、检查结果、发布地址／运行记录、未完成项。区分“本地验证通过”“部署完成”“线上验收通过”；没有真实部署证据不宣称发布成功。
