# 数据格式版本与迁移契约

本契约从应用 v0.1.1 起实施。项目配置为 v2，用于按类型属性及数组，兼容读取项目 v1；Markdown 模块现为 v2，增加 begin/end 边界与正文引用，兼容读取和编辑模块 v1。交换包外壳仍为 v1。集中版本定义在 `src/core/formats.ts`，文件转换在 `src/main/migrations.ts`，运行时校验与 JSON Schema 一起维护。

## 四种版本分别管理

| 概念 | 当前例子 | 用途 |
| --- | --- | --- |
| 应用版本 | 0.2.1 | 软件发布，与本地开发中的数据格式分别管理 |
| 数据格式版本 | 项目 2，模块 2，交换包 1 | 指明文件结构及语义，分别按数据域升级 |
| 插件 API | `apiVersion: 1` | 插件和应用的调用协议，与项目格式无关 |
| 文件内容版本 | SHA-256 | 乐观并发检查，不能代替格式版本 |

不使用应用版本判断数据能否读取，也不把哈希当作数据格式。显式版本值必须是受支持的正整数；字符串、非法数值与未来版本不能当作当前版本处理。

## 格式目录

| 数据域 | 标记 | 迁移与存储范围 |
| --- | --- | --- |
| 项目 YAML | `version: 2`，兼容 v1 | `.reqtype/project.yaml`；新增 `typeAttributes` 与数组定义 |
| Markdown 模块 | front matter 中 `reqtype: 2`，兼容 v1 | 所有需求块与正文引用继承模块版本，不逐条重复标记 |
| 需求元数据 | 字段结构沿用 `requirement-v1` Schema | UUID、编号、属性与业务关联不变，边界由模块版本决定 |
| 原生交换包 | `format: reqtype`、`version: 1` | 交换外壳独立定版本；内部配置、模块还需分别校验 |
| 本机渲染设置 | `format: reqtype.renderers`、`version: 1`、`payload` | `.reqtype/local/renderers.json` |
| 文件恢复日志 | `format: reqtype.transaction`、`version: 1`、`payload` | `.reqtype/local/transactions/` |
| 迁移备份 | `format: reqtype.migration-backup`、`version: 1` | `.reqtype/local/migrations/`；含迁移前后完整字节与哈希 |
| 最近打开项目 | `format: reqtype.preferences`、`version: 1`、`payload` | 应用 userData 的 `settings.json`，不随项目交换 |
| 插件启用状态 | `format: reqtype.plugin-state`、`version: 1`、`payload` | 应用 userData 的 `plugins/disabled.json` |
| AI 本机设置 | `format: reqtype.ai`、`version: 1`、`payload` | 应用 userData 的 `ai-settings.json`；凭据仅存系统安全存储的密文，不随 Git 或交换包分发 |
| 派生索引／缓存 | 可删除重建 | 不作为业务真相，不通过迁移改变需求数据 |

Schema 位于 `schemas/`。Markdown 的 v1／v2 front matter Schema 和共用元数据 Schema 校验解析后的结构，不直接校验整篇文本；真实边界与正文引用由模块解析器校验。路径、身份唯一性、类型定义、关联、哈希、大小限制和事务状态还需领域校验。Schema 在本地加载，不下载远程 `$id`。

## v0 的准确含义

v0 是迁移器内部对**实际已经存在的无版本旧布局**的编号，不是可以随意写入文件的 `version: 0`。当前仅识别：

- 有稳定模块 ID、缺少 `reqtype` 的旧模块：补充 `reqtype: 1`，保留其余源文本、BOM、换行、注释、未知字段、正文与身份。
- 0.1.0 的裸渲染设置对象：放入 v1 信封的 `payload`。
- 0.1.0 的裸事务日志：校验后放入 v1 信封的 `payload`。
- 裸最近项目对象与裸插件禁用 ID 数组：兼容读取；下一次对应设置操作写新信封前保存原文。

普通 Markdown 不自动成为模块，也不自动分配 UUID。缺少模块身份、损坏数据或重复身份需要先人工处理。项目配置和交换包没有已发布的 v0 格式，因此不猜测无版本配置或不明包的含义。

读取旧数据不等于批量升级。旧字段缺省值只在内存中补齐，不因打开项目而重排 Markdown 或改写项目 YAML。正常设置操作可以写入当前本机格式，但旧字节会通过事务或本机原文备份保留。旧 pending 日志的自动恢复是例外：先存档旧日志，再回滚未完成写入并更新恢复状态。

## 兼容性规则

- 保持原意且有安全默认值的可选字段可以留在同一格式版本；保留未知扩展字段。扩展推荐使用 `x-厂商名` 或命名空间，避免占用 `format`、`version`、`reqtype`、`id`、`module` 等核心字段。
- 删除、重命名、改变字段含义／类型、改变边界语法或关联语义，若旧读者可能误解，必须增加该数据域的整数版本。不得用增加必需字段却不升版的方式绕过兼容检查。
- 未来项目格式拒绝打开；未来模块按源码只读显示，不建立 v1 需求索引。磁盘保存、属性修改、模块补全和导入不能把它隐式降级。
- 未来交换包在解码文件前拒绝；未来恢复日志不执行回滚；未来迁移备份，以及条目目标版本高于当前支持版本的备份，不执行恢复。已知旧文件与未来文件混合时，整批迁移被阻止。
- 本机偏好未知时保留原文件、跳过最近项目记录更新；插件启用状态未知或损坏时停用插件，不将错误当作首次运行自动启用。
- 模块 v1 普通编辑继续写 v1；v2 新建条目使用 begin/end。已知模块版本的变化只能由显式迁移完成，普通保存拒绝直接升降级。AI 设置没有已发布的无版本旧布局；损坏或未来设置保留原文，不自动重置。
- 升级后也不承诺旧程序可写新格式。0.1.0 二进制不具备本契约的完整保护；如需退回，先停用新版并恢复对应旧文件，不要让两个版本同时编辑同一份项目。

## 显式项目迁移

设置页的“数据格式与迁移”提供检查、原文预览、升级和恢复。界面有未保存文档或设置时禁止升级／恢复。

1. **只读检查**：发现项目、模块、本机渲染设置及恢复日志，按格式分别识别；校验源数据及迁移后候选项目。
2. **确定性转换**：只运行应用自带的逐版本步骤 `N → N+1`，允许串联多步；步骤必须唯一、完整，且每步输出通过目标版本校验。当前步骤包括真实旧布局的 `0 → 1`、项目配置 `1 → 2`，以及 Markdown 模块 `1 → 2`。模块升级仅替换 front matter 版本、顶层真实起始／结束标记，代码示例及元数据 YAML 原样保留；不会把三括号示例转换成业务关联。
3. **预览绑定原文件**：记录受检查文件的清单和内容哈希，10 分钟有效；增加文件、外部修改或跨项目使用 token 都会拒绝执行。
4. **先备份后首写**：保存完整迁移前后字节、SHA-256、路径、格式域、版本和项目身份，再开始文件事务。备份成功之前不修改目标文件。
5. **事务应用**：逐文件检查版本并原子替换；中途失败回滚，后续启动可处理未完成事务。多文件事务不是操作系统级一次性原子提交，恢复日志负责中断后的恢复。
6. **明确恢复**：恢复前检查全部目标文件。只接受仍与迁移后哈希相同、或已经是迁移前原文的文件；发现后续编辑时整批拒绝，避免覆盖。重复恢复不会重复改写。

UUID、可读编号、关联目标、正文和附件不得因为格式升级被重新生成或重新编号。迁移可以转换有明确映射的已知字段，但不能顺便清理、格式化或修复不相关内容。附件当前不转换，原字节保留。现有格式无需变化时不创建迁移备份或改写文件。

迁移备份与事务日志保存在 `.reqtype/local/`，不进入 Git 或原生交换包，也不会自动删除。旧 pending 日志原文存于 `.reqtype/local/legacy-journals/`。最近项目与插件启用状态不属于项目，旧原文分别保存在对应设置目录的 `.format-backups/`；这些备份可能含本机路径，应按本机数据管理。

## 命令行

```sh
npm run data -- check /path/to/project
npm run data -- upgrade /path/to/project
npm run data -- backups /path/to/project
npm run data -- restore /path/to/project <备份ID>
```

默认动作是 `check`。检查不执行启动恢复、不写数据；退出码 0 表示可检查／可迁移，2 表示发现阻断项，1 表示命令或执行错误。`upgrade` 是显式写入命令，先打印计划再应用；建议先单独检查并保存、关闭其他编辑器的未保存内容。命令行无法得知其他进程的未保存草稿，但会检查磁盘哈希。

## 后续增加格式版本的交付要求

先定义真实的新语义，再增加对应域的版本、新版 Schema、逐版本转换和各源版本校验。保留原 v1 Schema 与冻结夹具，不通过重写历史夹具让新实现“通过”。项目 v1→v2 保留稳定身份与旧属性语义，将全局属性绑定到全部既有类型；不改动需求正文。见[条目模型](project-item-model.md)。

同时更新读写入口、预览／恢复、导入导出、插件快照兼容说明与回归矩阵。跨文件重组或新增／删除文件的迁移需要专门设计和用例，不能只把版本数字加一。

必须证明：链式迁移与一次升级语义一致、重复执行无额外修改、身份／正文／扩展／附件保留、未来版本拒写、过期计划拒绝、备份损坏拒绝、失败回滚、进程中断恢复，以及旧项目与新版项目的完整交换。合成多步链验证迁移引擎，不表示已经实现业务格式 v3。
